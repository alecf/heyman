CRITICAL ISSUES
================================================================================

1. RACE CONDITION: Spinner active flag and message field
   File: internal/spinner/spinner.go
   Lines: 18, 38, 57-58, 70, 73
   Problem: Unsynchronized access to 'active' and 'message' fields from multiple goroutines
   Risk: Memory corruption, undefined behavior, crashes
   Fix: Add sync.RWMutex to Spinner struct

2. CHANNEL PANIC: Sending on closed channel in query executor
   File: internal/cli/query_executor.go
   Lines: 36, 46-48, 64-66, 70
   Problem: Channels closed by provider while consumer still processing
   Risk: Runtime panic "send on closed channel", goroutine leaks
   Fix: Ensure channels fully drained on error paths, use context cancellation

3. GOROUTINE LEAK: OpenAI StreamQuery
   File: internal/llm/openai.go
   Lines: 65-122
   Problem: Unbuffered channels block indefinitely if caller stops reading
   Risk: Goroutines accumulate, memory leaks, resource exhaustion
   Fix: Buffer channels (10+ capacity), check context.Done() before sends

MEDIUM SEVERITY ISSUES
================================================================================

7. RACE CONDITION: Cache concurrent access
   File: internal/cache/cache.go
   Lines: 41-72
   Problem: Multiple goroutines can read/write cache files simultaneously
   Risk: Cache corruption, lost metadata updates, TOCTOU race
   Fix: Add sync.RWMutex to Cache struct

8. CHANNEL PANIC: Double close of spinner done channel
   File: internal/spinner/spinner.go
   Lines: 74, 91
   Problem: Stop() and StopWithMessage() both close done channel
   Risk: Runtime panic "close of closed channel"
   Fix: Use sync.Once for channel close

9. DEADLOCK POTENTIAL: Query executor doesn't monitor context
   File: internal/cli/query_executor.go
   Lines: 42-68
   Problem: Select loop doesn't check ctx.Done(), can hang indefinitely
   Risk: Application hangs, timeout, resource exhaustion
   Fix: Add case <-ctx.Done() to select statement
